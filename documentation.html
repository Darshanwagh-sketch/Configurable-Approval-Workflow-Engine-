Configurable Approval Workflow Engine

Comprehensive Architectural Blueprint, Domain Model, Request Flow, Exception Handling & API Reference

Author: Senior Java Backend Engineering Team  |  Stack: Java 21, Spring Boot 3.3.5, Spring Security (JWT), Spring Data JPA, H2, JaCoCo (96% Coverage)  |  Target Use Cases: Employee Leave Requests, Expense Claims, Purchase Orders

1. Executive Summary & Core Objective

The Configurable Approval Workflow Engine is an enterprise backend service built to automate multi-stage approval sequences without hardcoding workflow routes or business rules into the source code.

CRITICAL ARCHITECTURAL RULE: Zero Hardcoded Workflows
The engine contains no if-else or switch-case statements based on request types (LEAVE, EXPENSE), role names, or step sequences. All approval steps, sequences, and role authorities are loaded dynamically from the database. Adding a new request type or altering an existing sequence requires only inserting or updating database records.

Key Architectural Guarantees

  • N-Step Workflow Agnostic: Works seamlessly for 1-step (QUICK_REQUEST), 2-step (LEAVE, EXPENSE), 3-step (PURCHASE_ORDER), or any $N$-step sequence.
  • Workflow Versioning / Snapshots: Requests capture the active workflowVersion at submission time. Mid-flight requests are immune to database configuration changes.
  • Concurrency Control: Implements JPA @Version optimistic locking to guarantee that concurrent approvals cannot duplicate step advancements.
  • Immutable Append-Only Auditing: Every action generates a tamper-proof audit record in approval_history. No updates or deletions are exposed.
  • Stateless JWT Security: Signed HMAC-SHA256 tokens authenticate all business endpoints. Requesters are strictly prohibited from approving their own requests.

4. End-to-End Request Flow

The following step-by-step breakdown illustrates how a request flows through the entire system architecture:

1
Authentication & Security Interception (POST /auth/login)
Client submits credentials. Spring Security verifies the BCrypt hash. JwtService issues a signed HMAC-SHA256 token containing the username and authority claim (e.g., ROLE_REQUESTER). On all subsequent calls, JwtAuthenticationFilter validates the Bearer token and establishes the SecurityContext.
2
Request Submission (POST /requests)
The client submits {"type": "LEAVE", "payload": {"days": 3}}. SecurityUtils extracts the creator identity directly from the authenticated principal (never trusting client-supplied author headers). WorkflowConfigurationService queries the database for active steps for LEAVE. Request is saved with status PENDING, currentStepOrder = 1, and an immutable REQUEST_CREATED history entry is saved in the same transaction.
3
Step Approval & Sequence Advancement (POST /requests/{id}/approve)
Approver submits approval. The engine enforces domain rules:
  1. Status must be PENDING (otherwise throws WorkflowTransitionException → 409 Conflict).
  2. Self-approval check: request.createdBy != approverUsername (otherwise throws UnauthorizedActionException → 403 Forbidden).
  3. Role check: Approver's role must match the database-configured role for currentStepOrder (otherwise throws 403 Forbidden).
Engine writes an APPROVED record to history. It then queries the DB for currentStepOrder + 1:
  • If a next step exists: Request advances to currentStepOrder = 2.
  • If no next step exists: Request transitions to terminal status APPROVED and sets currentStepOrder = null.
4
Workflow Rejection (POST /requests/{id}/reject)
An authorized approver rejects the request. The engine validates authorization, appends a REJECTED audit event with mandatory/optional remarks, transitions status to REJECTED, and sets currentStepOrder = null. Workflow is permanently terminated.
5
Emergency Administrator Override (POST /admin/requests/{id}/override)
An ADMIN user can force-override any request to APPROVED or REJECTED at any time. The engine verifies the user is an admin, checks that the target status is different from current status (idempotency guard), updates status, and appends ADMIN_OVERRIDE_APPROVED or ADMIN_OVERRIDE_REJECTED to history without removing past records.

5. Centralized Exception Handling & HTTP Status Code Mapping

Exception handling is implemented in two tiers: at the Security Filter Layer and via a centralized @RestControllerAdvice in GlobalExceptionHandler.java.

Exception Class HTTP Code Error Title Trigger Condition
MethodArgumentNotValidException 400 Bad Request Validation Failed Bean validation fails (e.g. blank username, blank password, empty request type).
InvalidWorkflowException 400 Bad Request Invalid Workflow Configuration Requested type has no active steps configured in database, or step sequence has gaps.
BadCredentialsException 401 Unauthorized Authentication Failed Invalid username or password supplied during login.
AuthenticationEntryPoint 401 Unauthorized Unauthorized Client calls protected business endpoint without a valid Bearer JWT.
UnauthorizedActionException 403 Forbidden Forbidden Action Requester attempts self-approval; or non-admin attempts registration for ADMIN role.
AccessDeniedException 403 Forbidden Access Denied User role does not have authorization for endpoint or attempting to view another user's request.
ResourceNotFoundException 404 Not Found Resource Not Found Request ID, User, or Step cannot be found in the database.
WorkflowTransitionException 409 Conflict Invalid State Transition Attempting to approve or reject a request that is already approved, rejected, or completed.
UserAlreadyExistsException 409 Conflict User Conflict Attempting to register with a username that already exists in the database.
OptimisticLockingFailureException 409 Conflict Concurrent Modification Conflict Two concurrent threads attempt to advance the exact same request simultaneously.
Exception (General) 500 Server Error Internal Server Error Unhandled runtime crashes. Logged via SLF4J internally; stack traces never leak to client.

Standardized JSON Error Payload Format:

{
  "timestamp": "2026-10-28T14:20:00Z",
  "status": 403,
  "error": "Forbidden Action",
  "message": "A requester cannot approve their own request.",
  "path": "/requests/1/approve"
}

6. REST API Endpoint Specifications

Method Route Authorized Roles Description Success Code

POST /auth/register Public Registers new user account (REQUESTER or APPROVER only). 201 Created

GET /requests/{id} REQUESTER, APPROVER, ADMIN Retrieves metadata, payload, and dynamic current step role (privacy restricted). 200 OK
POST /requests/{id}/approve APPROVER, ADMIN Approves active step; advances sequence or completes workflow. 200 OK
POST /requests/{id}/reject APPROVER, ADMIN Rejects request and terminates workflow. 200 OK
GET /requests/history/{id} REQUESTER, ADMIN Returns complete immutable chronological audit trail. 200 OK
POST /admin/requests/{id}/override ADMIN Emergency override to APPROVED or REJECTED with mandatory remarks. 200 OK
